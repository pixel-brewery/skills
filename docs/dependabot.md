# Automatic dependency updates

Dependabot proposes all supported dependency updates, including major versions. Related framework packages are grouped. Updates merge only after the exact current head passes every configured verification job and GitHub enforces the protected, up-to-date base. The controller creates no reviews or replacement checks and changes no branch rules.

The trusted controller runs default-branch code without checking out pull-request code, installing its dependencies or executing downloaded artifacts with write credentials. Nx repositories keep this dependency-free implementation inside their existing executor owner; other repositories use the dedicated workflow script owner. The privileged workflow invokes the same implementation directly to avoid a privileged package installation.

An eligible pull request must belong to this repository, target `main` and retain the actual Dependabot author identity. Before accepting a native CI result, the controller proves the live default commit M, bot head B and synthetic PR merge C: both live refs match, M is an ancestor of B, C has exactly the ordered parents [M, B], and its tree equals B's tree. The workflow must be the configured active workflow and be uniquely associated with this exact PR and head.

A native `pull_request` run that concludes `action_required` can be authorized through GitHub's workflow-approval endpoint. This is limited to actual Dependabot or GitHub Actions bot actors with their immutable platform IDs. The complete CI files at M and B are verified as Git blobs. They must be identical except for complete action-use lines retaining their owner/repository/path while changing a full 40-hex commit pin and its version comment. Explicit root/job token permissions must remain read-only or empty. Custom secrets, inherited secrets, YAML aliases/merges, ambiguous mapping syntax, reusable job workflows and environment-secret contexts are rejected rather than guessed. The native `github.token` and exact `secrets.GITHUB_TOKEN` alias remain permitted under those read-only scopes. The controller rechecks the current PR, M/B/C refs, native run and current attempt before its approval POST. Approval itself is never successful verification.

Only actual native PR runs participate in merge-proof selection. The latest eligible native run is fetched again, and its current attempt must complete every configured job successfully at B. An approved second attempt on the same run ID remains eligible even if a newer diagnostic dispatch exists. A maintainer-triggered native PR run after a legitimate dependency correction can qualify; the strict service-actor restriction applies to authorization of blocked runs. Failed, skipped, missing or superseded jobs block merging. Immediately before the SHA-guarded squash merge the controller repeats the live source, run-attempt, association and protection checks. GitHub still enforces its ordinary branch rules.

Stale branches are refreshed using their expected head. Explicit `workflow_dispatch` verification remains available for diagnosis at the requested SHA under the same immutable CI, read-only permission and live-ref proof, but never counts as a required PR check or substitutes for the native PR workflow. Scheduled and manually retried reconciliation use the same complete proof routine as workflow completion events.

Mosaik starter lockfiles retain their manifest's `latest` root specifications. The only automatic lockfile repair changes erroneous `*` Mosaik root entries back to `latest`; resolved package versions and integrity data remain unchanged. The repaired head requires its own successful native verification.

Native-token merges may suppress push workflows. After a confirmed merge the controller can request configured main verification and affected existing Pages workflows. Continuation requires the uniquely associated, actually merged bot PR and its exact merge SHA still at current `main`, rechecked before dispatch. Deduplication uses the configured workflow identity, repository, branch, SHA and run attempt; foreign or diagnostic-branch entries cannot suppress it. A genuine existing main push/dispatch run is retained in every state, including failure or cancellation. The controller does not blindly rerun failed CI or releases. A scheduled retry can recover the current confirmed merge even when unrelated updates have displaced it from the recent-closed list. No package release is introduced.

Reconciliation isolates failures by pull request: a conflicting or concurrently changed bot branch cannot prevent other eligible updates from being processed. The controller reports failed PR numbers after the batch, preserving failure visibility and scheduled recovery. API diagnostics include only the operation, endpoint and HTTP status; response bodies and credentials are omitted.
