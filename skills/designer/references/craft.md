# Compose, redesign and finish

Use after discovering the target and its foundations. These workflows adapt [UI Craft](ui-craft.md) to Mosaik's catalog, components and tokens.

## Compose a surface

Establish the audience, the task they came to complete and the primary action. Inspect the catalog before choosing a composition. In one short statement, describe the layout and why it supports the task: for example, a customer table with filters above it and details beside the selection. A request for a small correction does not need a full design brief.

Use a suitable existing template or recipe first, adapting its documented options. When none fits, arrange real Mosaik components around the content hierarchy. Choose density from the task and established product, not from an imported aesthetic preset. A dashboard needs useful information and clear comparisons; a landing page needs a readable proposition, evidence and a next step. Neither implies a grid of identical cards.

Build the shell and main task first, then secondary content and the applicable [interaction states](interaction.md). Keep one dominant primary action per view, quiet supporting actions and semantic status colors. Use realistic, internally consistent sample data; mark invented content as examples. Do not invent customer endorsements, live statistics or working integrations.

Use typography roles, spacing, grouping and alignment to establish hierarchy before adding decoration. Charts, progress indicators, tables and controls come from the documented Mosaik catalog. Native flex/grid handles layout on application and Claude Design surfaces; Studio follows its current authoring contract.

## Redesign an existing surface

Inspect the current screen and map its routes, content, important states, navigation and primary workflows. Preserve the user's brand and working behavior unless the request explicitly changes them. Identify the concrete problem before choosing how much to change: an alignment correction, a visual refresh, a new composition or a larger rebuild.

Reuse existing components, route owners and data contracts. Keep filter state, selections, validation, keyboard behavior and accessible names when moving controls. Check the same main flow before and after. A visual redesign does not authorize new persistence, authentication, business behavior or dependency migrations.

## Focused passes

| Request | Apply |
| --- | --- |
| Simplify or quieter | Remove redundant sections, repeated labels and competing emphasis; keep necessary information and discoverable actions |
| Bolder or more expressive | Strengthen hierarchy, composition or a justified theme override; preserve readability, status meaning and task completion |
| Typography | Use the existing theme's roles, readable line lengths, aligned labels and sensible wrapping; use tabular numerals where the current font supports them for compared values |
| Color | Preserve neutral chrome and semantic statuses; change intentional theme/preset sources rather than scattering literal colors |
| Copy | Name actions by what happens; make errors specific with a recovery path; explain empty states and clarify destructive consequences |
| Polish | Correct alignment, spacing rhythm, long content, icon consistency, numeric/date formatting and hover/focus/pressed/disabled feedback |

Do not turn polish into a new theme or add a decorative “signature” when a restrained interface already serves the product. Motion follows [interaction](interaction.md) and the existing stack.

## Completion

Verify the actual screen and primary task, supported color modes, useful narrow and wide layouts, keyboard operation and meaningful failure states. Run the skill checker and the consuming project's focused checks. Fix issues within an implementation request; a review reports evidence and priorities without changing files. Describe the result and verification limits without inventing a score or claiming checks that were unavailable.
